# レビュー用 差分ドキュメント生成

大きい差分を人間がレビューするとき、GitHub の Files changed だけでは「どこが本題で、何を見落としてはいけないか」が分からない。このスキルは差分に解説を重ねた1枚のHTMLを作る。

**差分は git から機械生成し、解説だけを書く。** 差分を書き写さないのでトークンを使わず、書き写し間違いも起きない。

## 使い方

```bash
python3 ~/.claude/skills/review-diff-docgen/assets/gen_review.py <notes.py> <base>...<head> <out.html>
```

`notes.py` は `assets/notes.template.py` をコピーして書く。**この2つ以外のファイルは作らない。** 機構（`gen_review.py`）は案件ごとに触らない。

## 手順

### Phase 0 — HTMLにする価値があるか判断する

**差分が小さい（数ファイル・100行未満）なら作らない。** GitHub をそのまま見るほうが速い。「変更が多くて全部は追えない」「レビュアーに文脈を渡したい」ときだけ作る。

### Phase 1 — 差分を把握する

```bash
git diff <base>...<head> --stat
git diff <base>...<head> --numstat | awk '{print $3, $1"/"$2}'
```

**実装とテストの行数比を最初に見る。** これがレビューの読み方を決める。実装が全体の1割しかないなら、それをそのまま伝えるのが最大の価値になる。

差分の中身は必要な範囲で読む。**読んだ内容を notes に書き写さない** — 差分はHTMLに自動で載る。書くのは「差分を読んでも分からないこと」だけ。

### Phase 2 — notes.py を書く

雛形をコピーする。

```bash
cp ~/.claude/skills/review-diff-docgen/assets/notes.template.py notes.py
```

**`groups` の判定関数を対象リポジトリに合わせる。** ここだけは必ず書き換える。言語別の例は雛形のコメントにある。最後のグループは必ず全捕捉（`lambda p: True`）にする。

各フィールドの書き方は下の「解説の書き方」を参照。

### Phase 3 — 生成して検証を読む

```bash
python3 ~/.claude/skills/review-diff-docgen/assets/gen_review.py notes.py <base>...<head> out.html
```

標準出力の**実測値と検証結果を必ず読む**。生成物は使い切りで、後からHTMLを直す運用は存在しない。誤りはここで潰す。

- `⚠ 検証で N 件の指摘` が出たら、notes を直して**再生成する**
- `解説が無いファイル` → `file_notes` に追記
- `file_notes のキーが差分に存在しない` → パスの誤りか、解説が外れている
- `そのファイルの現在の内容に無い` → 途中状態を書いている疑い。最終コードを確認する
- `実測値にも verified_numbers にも無い数量表記` → 値を直すか、根拠を `verified_numbers` に登録する

グループ別のファイル数が想定と合っているかも確認する。合わなければ判定関数が誤っている。

### Phase 4 — 見て確かめる

ブラウザで開き、**図を入れた場合は必ず目視する**。SVGは座標がハードコードなので、テキストが箱からはみ出しても検証では捕まらない。狭い幅（分割ペイン）でも読めるか確認する。

## 解説の書き方

**差分を読めば分かることは書かない。** 書くのは次の4つ。

1. **なぜそう書いたか** — 選択肢があった箇所の判断理由
2. **見落としやすい前提** — 「この変数は `$card` であって `$user` ではない」など
3. **既存構造との関係** — 「この非対称は今回作ったものではない」
4. **このPRで壊れうるもの** — レビュアーが承認を判断する材料

### highlights（要点）

3〜6個。**「このPRで壊れうるもの」を1つ入れる。** これがないとレビュアーは「動く/動かない」しか判断できず、リスクの承認ができない。

`level` は `core`（本題）/ `warn`（判断が要る）/ `note`（経緯）。

### file_notes（ファイル別）

**テストは `{"guarantee": ...}` を使う。** テストは展開せず読み飛ばされる前提なので、「何を担保しているか」を折りたたみの外に出す。実装の説明は `note` に回す。

```python
"src/foo.test.ts": {
    "guarantee": "担保: 同じ入力なら同じURLになり、更新時だけ変わる",
    "note": "時刻を固定して完全一致で検証する（相対比較では退行を検出できないため）",
},
```

実装ファイルには `guarantee` を付けない。差分を読む前提なので要約は不要。

### 検証を通すための規律

生成時の検証がこれを前提にしている。

- **メソッド名は `foo()` の形で書く。** 括弧なしだと識別子として拾えず、存在しないメソッド名を書いても検出できない
- **数字は実測値を使う。** 導けない数字（既存コードの構造など）は `verified_numbers` に根拠ごと登録する。根拠を残さずに書けない仕組みになっている
- **差分に現れないコードの構造を断定しない。** 検証できないので誤りが残る
- **途中の設計変更を最終状態と混ぜない。** 「Aにした」と書いたのに最終コードがBなら検証が捕まえる

### 図（DIAGRAM_SVG）

**変更の因果が図で伝わるときだけ入れる。** 空文字なら図のセクションごと出ない。

図は解説文全体の7割前後のトークンを食う。座標がハードコードで、AIは描画結果を見られないため箱からのはみ出しを検証できない。**要素を減らすほど破綻しにくい。** 雛形は `references/diagram-patterns.md`。

図に矢印を描くときは、**その参照関係が実際にコードに存在するか確認する。** 説明文と線が矛盾していると誤読を招く。

## 出力されるHTML

- 統計（コミット数・ファイル数・実装/テストの行数比）
- 要点（level 別に色分け）
- Before/After の対比
- 構造図（任意）
- 差分（グループ分け、GitHub風の行番号2列、既定で実装だけ開く）
- コメント機能（ドラッグ選択 → 入力 → Markdown コピー。localStorage に保存され外部送信なし）

差分行を選択してコメントすると、**ファイルパスと行番号が自動で記録される**。「まとめてコピー」で Markdown 化してPRに貼れる。

## 制限

- 1ファイル400行を超える差分は先頭200行だけ表示する。ロックファイル・生成物（`*.lock`, `dist/`, `vendor/` 等）は差分本体を省略する
- `<base>...<head>` の形式が必須。単一リビジョンは拒否する（`git log` が全履歴を返すため）
- リネームは新パスとして扱う。旧パスに紐づけた `file_notes` は外れる
- コメントは保存先がブラウザなので、環境をまたいで共有できない。Markdown 化して渡す
